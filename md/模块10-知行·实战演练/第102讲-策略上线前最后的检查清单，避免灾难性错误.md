# 第102讲 策略上线前最后的检查清单，避免灾难性错误

> 风险提示：本文仅用于量化投资知识教育，不构成任何投资建议。实盘交易部署会产生真实损失，必须经过授权、测试和独立风控。

## 本讲目标

- 完成数据、模型、工程、风险和运营五类检查。
- 明确上线批准与回滚条件。
- 形成可签署的发布清单。

## 上线是风险事件

策略从研究进入真实账户后，错误会变成现金流。上线清单的作用是阻止“大家都以为别人检查过”。

## 数据

来源、许可、时区、复权、公告时间、缺失与备用源已确认；历史与实时字段一致；断流和异常能告警。

## 模型

代码锁定、无前视、样本外与稳健性通过；参数来源清楚；特征和预测有漂移阈值；已知失效环境记录。

## 执行

订单类型、最小单位、涨跌停、停牌、部分成交、重复回报、重启恢复和撤单已测试；交易成本与容量压力后仍可接受。

## 风险

单资产、行业、因子、杠杆、流动性、回撤和压力损失限额已配置；限额在独立层执行；紧急停机与减仓可用。

## 运营

权限最小化、密钥安全、时钟同步、监控值班、券商对账、版本发布和事故手册完备。

## 发布与回滚

采用小资金、少品种、分阶段放量；记录批准人、版本和生效时间。回滚到上一版本与清仓不是同一动作，都需预案。

## 最后问题

如果负责人今天无法上线，你能否仅凭文档安全运行和停止系统？若不能，项目还未准备好。

## 把检查项改成发布门禁

清单只有“是/否/不适用”、证据链接、检查人和批准人，才能阻止带病上线。关键项未通过时系统应拒绝发布，而不是在会议里口头承诺以后补。标记“不适用”也要写理由。

研究、工程、交易和风险应分别签署自己负责的部分，避免同一作者既开发、又验收、又批准全部环节。

## 发布前做一次全链路演练

使用与生产相同的数据接口、调度、代码包和配置，在不发送真实订单的影子环境跑完整交易日。核对数据到达、信号、风控、订单意图、账本、告警与日终报告，再模拟重启和备用源切换。

演练通过的是指定版本与环境；代码、参数或基础设施发生实质变化后，需要重新评估受影响门禁。

## 紧急停止要区分三种动作

“停止开新仓”保留现有头寸但不增加风险；“撤销未成交订单”阻止挂单继续成交；“平掉现有仓位”主动改变风险并可能造成冲击。这三种动作不能共用一个含糊的停机按钮。

预案应规定各自触发条件、权限、执行顺序和无法成交时的处理。定期演练控制面，确认在主系统故障时仍能独立生效。

## 回滚代码不等于回滚市场状态

软件可以恢复到上一版本，账户持仓和已成交订单却不能自动回到过去。回滚前要读取真实账户状态，判断旧版本是否理解当前持仓与订单；必要时进入只减仓安全模式，而不是直接启动旧策略。

数据库结构、特征版本和配置也要向后兼容。发布包应明确代码回滚、配置回滚、模型回滚和头寸处置是四项不同操作。

## 分阶段上线的证据阶梯

建议按影子运行、模拟交易、小资金少品种、受限扩大和正式规模逐级推进。每一级都有最短观察条件、最大风险、晋级指标和退回条件。观察条件应包含足够信号和异常事件，不只看运行天数。

放量时同时评估成交冲击和容量，不能按小资金收益线性外推。

## 上线后的首日与首周计划

明确值班人、检查频率、关键仪表盘、账户对账时间和升级通道。首日重点核对订单与账本，首周关注数据与成本偏差；达到稳定条件后再转入常规监控。

任何人工覆盖都要记录原因、批准人、有效期和恢复动作。临时修改若没有过期机制，最终会变成无人记得的永久规则。

## 最终签署包

签署包应包含策略说明、研究报告、数据与模型版本、代码提交、测试结果、压力与容量、监控面板、事故手册、权限表、发布计划、回滚演练和已知风险接受记录。未参与开发的人应能据此安全启动、观察、降级和停止系统。

## 实战交付：让别人能够独立复现

围绕“策略上线前最后的检查清单，避免灾难性错误”形成可交付的研究闭环。完工标准不是代码在作者电脑上运行过一次，而是另一位读者能按说明重建环境、运行测试并解释输出。

1. 冻结需求、输入字段、参数、信号时点、成本口径和输出结构。
2. 把数据校验、策略逻辑、账本、指标、日志和异常处理拆成可测试模块。
3. 使用同一份输入分别运行 Python 与 R，实现逐日结果与指标对账。
4. 保留 README、运行命令、测试记录、已知限制和上线前检查清单。

## 证据、边界与风险

- **参考资料**：
  - [Backtrader 官方文档](https://www.backtrader.com/docu/)：事件驱动回测框架的行为定义。
  - [Python logging 官方文档](https://docs.python.org/3/library/logging.html)：结构化日志与严重级别的实现依据。
- **适用条件与边界**：平台回测结果取决于撮合、费率和数据实现；模拟交易仍不能完整复现实盘排队、冲击和故障。
- **主要失败模式**：研究与生产代码分叉、日志不可追溯、上线无回滚、告警无责任人、收益无法归因。

## 常见误区与修正

- 只交付代码片段而没有输入、环境和运行说明；这不构成可复现产物。
- Python 与 R 使用不同默认参数或缺失值规则；跨语言对账必须逐列进行。
- 把回测通过等同于可实盘；模拟交易、权限隔离、监控和故障恢复仍需独立验收。

## 实战验收清单

- [ ] 从干净环境可按 README 一次运行成功
- [ ] 输入校验和关键逻辑有自动测试
- [ ] Python 与 R 输出在约定容差内一致
- [ ] 日志、监控、异常恢复和风险限制均有文档

## 本讲小结

- 上线清单覆盖数据、模型、执行、风险和运营。
- 发布应分阶段，并具有明确回滚与停机方案。
- 职责、版本和批准必须可审计。
